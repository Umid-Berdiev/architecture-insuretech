# Задание 1. Технологическая архитектура InsureTech (to-be)

Файлы:

- `InureTech_технологическая архитектура_to-be.drawio` — схема в draw.io (нотация библиотек Yandex Cloud, как в as-is схеме).
- `InureTech_технологическая архитектура_to-be.png` — экспорт схемы.

Целевые показатели: доступность 99,9 %, RTO 45 мин, RPO 15 мин, работа 24/7 для всех
часовых поясов, одинаковое время загрузки страниц из всех регионов РФ, объём данных 50 GB.

## Принятые решения

1. **Масштабирование и отказоустойчивость.** Горизонтальное масштабирование stateless-сервисов
   (HPA по CPU/RPS, Cluster Autoscaler для node group). Вертикальное — только для хоста PostgreSQL:
   50 GB не требуют распределённой БД. Приложение разворачивается в трёх зонах доступности одного
   региона (ru-central1-a/b/d): в одной зоне 99,9 % и RTO 45 мин при отказе зоны недостижимы.
2. **Kubernetes.** Один региональный кластер Managed Service for Kubernetes (мастера в трёх зонах,
   node group в каждой зоне), а не три независимых кластера: один набор манифестов и pipeline,
   один Ingress/backend group для ALB, podAntiAffinity и topologySpreadConstraints распределяют
   реплики по зонам, отказ зоны обрабатывает сам планировщик. Задержка между зонами региона < 2 мс.
   Независимые кластеры оправданы только при геораспределении между регионами, а в Yandex Cloud
   для РФ доступен один регион.
3. **Балансировка и health checks.** Cloud DNS (TTL 60 с) → anycast-IP Application Load Balancer (L7)
   → ingress-узлы трёх зон (веса 1:1:1). Партнёрский API выделен в отдельный backend с rate-limit
   20 RPS на API-ключ. Статика React SPA отдаётся через Yandex Cloud CDN с origin в Object Storage,
   поэтому время загрузки страницы не зависит от региона пользователя. Health checks:
   ALB → ingress `GET /healthz` каждые 2 с (таймаут 1 с, 3 неудачи → зона исключается);
   kubelet → поды readiness/liveness `GET /actuator/health` 10 с; Patroni → лидер PostgreSQL
   через DCS 10 с; CDN → origin при cache-miss. Результаты уходят в Yandex Monitoring + Alerting.
4. **Failover.** Active-active по трём зонам, без «тёплого резерва». Отказ зоны: ALB исключает её
   ingress за ≈ 6 с, клиент видит только ретрай (идемпотентные GET, POST с idempotency-key).
   Отказ мастера БД: Patroni за ≈ 30 с продвигает синхронную реплику, rw-FQDN переключается
   автоматически. Фактический RTO < 5 мин, RPO ≈ 0 при отказе зоны.
5. **База данных.** Managed Service for PostgreSQL, 3 хоста по одному в зоне: master,
   синхронная реплика (кандидат на failover, RPO ≈ 0), асинхронная реплика для чтения тарифов и
   отчётов. HA на Patroni + DCS. Бэкапы: ежедневный полный + непрерывный WAL-архив
   (archive_timeout 5 мин) в Object Storage → PITR на любую точку; восстановление 50 GB ≈ 15–20 мин,
   что укладывается в RTO 45 мин; хранение 7 дней, еженедельная проверка восстановления.
6. **Шардирование не применяется.** 50 GB и десятки RPS на запись помещаются на один хост с запасом
   на порядок; шардирование добавило бы роутер, кросс-шардовые транзакции и усложнение бэкапов без
   выигрыша. Пересмотреть при > 1 TB или > 5 000 RPS на запись; естественный ключ на будущее —
   `client_id`.
