## 1. Пользовательский путь и требования

1. Клиент заполняет заявку на ОСАГО в веб-приложении.
2. Сервис отправляет заявку во все подключённые страховые компании (СК) и опрашивает решения.
3. Предложение каждой СК показывается клиенту сразу, как только оно получено.
4. Максимальное ожидание решения СК — 60 секунд.
5. Пиковая нагрузка — до 2 500 одновременных пользователей, создающих заявку.
6. Все СК предоставляют однотипный REST API: «создать заявку», «получить предложение по заявке».

Решения, принятые с командой заранее: подход из задания 3 сохраняется (каждая СК опрашивается
отдельным адаптером со своими таймаутом, retry и circuit breaker); взаимодействие с СК выносится в
отдельный сервис `osago-aggregator`; всё остальное по ОСАГО (заявка, сбор предложений, выбор,
оплата, оформление полиса) остаётся в `core-app`.

## 2. osago-aggregator

### 2.1. Нужно ли своё хранилище — да, `osago-aggregator-db` (PostgreSQL)

Сервис не «прозрачный прокси», а оркестратор длительного (до 60 с) процесса с состоянием.
Для каждой заявки нужно хранить:

- идентификатор заявки core-app и идентификаторы, выданные каждой СК (без них невозможно опросить
  предложение);
- дедлайн заявки (момент создания + 60 с) и статус по каждой СК (создана / ожидает / получено
  предложение / отказ / таймаут / ошибка);
- полученные предложения — для повторной публикации при сбое Kafka и для разбора инцидентов;
- `lease` опроса: какой экземпляр сервиса и до какого момента ведёт опрос заявки (см. раздел 6).

Хранить это в памяти нельзя: при перезапуске или масштабировании пода заявки «потерялись бы», а
клиент ждал бы 60 с впустую. Kafka в роли хранилища тоже не подходит: нужен произвольный доступ по
ключу и обновление состояния, а не лог. Поэтому сервис получает собственную схему в PostgreSQL —
как и остальные сервисы InsureTech (одна схема на сервис).

### 2.2. API для core-app — события Kafka

| Направление | Топик | Ключ | Содержимое |
|---|---|---|---|
| core-app → osago-aggregator | `osago.requests` | id заявки | команда «обработать заявку»: данные автомобиля и водителей, id клиента, список СК, дедлайн |
| osago-aggregator → core-app | `osago.offers` | id заявки | одно событие на каждый ответ СК: `offer` (условия, премия), `declined`, `timeout`, `error`; плюс итоговое событие `completed`, когда ответили все СК или истёк дедлайн |

- Ключ — id заявки: все события одной заявки попадают в одну партицию, порядок внутри заявки
  сохраняется, а разные заявки обрабатываются параллельно.
- `osago.requests` публикуется через уже существующий Transactional Outbox core-app
  (`outbox` → Debezium → Kafka): заявка и команда записываются одной транзакцией, поэтому
  невозможна ситуация «заявка создана, а СК не опрошены» или наоборот.
- Потребители идемпотентны: osago-aggregator игнорирует команду с уже известным id заявки
  (повторная доставка после сбоя), core-app записывает предложение по паре (id заявки, id СК) —
  upsert.
- Контракты событий — в Schema Registry, как и остальные события из задания 3.
- Необработанные после повторов сообщения уходят в `osago.requests.dlq` / `osago.offers.dlq`.

### 2.3. Средство интеграции core-app ↔ osago-aggregator — Kafka в обе стороны

Почему не синхронный REST-вызов:

- обработка заявки длится до 60 с, держать HTTP-соединение (и поток) на всё это время — та же
  проблема нехватки ресурсов, что в задании 2; при 2 500 одновременных заявках это 2 500 открытых
  соединений только между двумя внутренними сервисами;
- ответы приходят от СК в разное время, а бизнесу нужно показывать каждое предложение сразу —
  поток событий естественнее, чем один ответ «всё готово»;
- Kafka уже есть в архитектуре (задание 3) и даёт буфер на пике рекламной кампании: если
  osago-aggregator временно не успевает, команды ждут в топике, а не теряются с ошибкой 503;
- перезапуск любого из сервисов не прерывает процесс: потребитель продолжает с сохранённого offset.

Задержка доставки через Kafka — десятки миллисекунд, что несущественно на фоне ответа СК.

## 3. API веб-приложения в core-app и средство интеграции

### 3.1. API

| Метод | Назначение |
|---|---|
| `POST /osago/requests` | создать заявку. Возвращает `202 Accepted` и id заявки сразу, не дожидаясь СК. core-app сохраняет заявку и пишет команду в outbox |
| `WS /osago/requests/{id}/offers` | WebSocket: сервер отправляет клиенту каждое предложение по мере поступления, затем событие завершения (все ответили или прошло 60 с) |
| `GET /osago/requests/{id}` | текущее состояние заявки и уже полученные предложения. Используется при открытии страницы заново и после переподключения WebSocket |
| `POST /osago/requests/{id}/choose` | выбор предложения, дальше — существующий путь оформления и оплаты |

Таким образом WebSocket используется только для доставки событий «сверху вниз», все действия
клиента остаются обычными REST-запросами, а состояние всегда можно восстановить через `GET`.

### 3.2. Средство интеграции — WebSocket (отдельная стрелка на диаграмме)

Рассмотренные варианты:

- **Polling** с фронтенда (REST раз в 1–2 с): при 2 500 пользователях это 1 250–2 500 RPS на
  core-app ради пустых ответов — воспроизводим проблему №1 из описания компании.
- **Server-Sent Events**: односторонний поток, подошёл бы, но WebSocket одинаково хорошо
  поддерживается браузерами и балансировщиком и оставляет возможность двусторонних сообщений
  (например, отмена заявки без отдельного запроса).
- **WebSocket** — выбран. Одно соединение на заявку на время до 60 с, сервер пушит предложения
  немедленно. Соединение закрывается по событию завершения.

Остальные взаимодействия веб-приложения с core-app остаются REST, поэтому на диаграмме две стрелки:
REST (создание заявки и прочее) и WebSocket (поток предложений).

## 4. Паттерны отказоустойчивости

Обозначения на диаграмме — из библиотеки курса (TimeOut, Retry, Rate Limiter, Circuit Breaker);
иконки стоят рядом со стрелкой, к которой относятся.

| Где | Паттерн | Параметры | Зачем |
|---|---|---|---|
| Веб → core-app, `POST /osago/requests` | Rate Limiter | 5 заявок в минуту на клиента | защита от «кликов по кнопке» и скриптов: каждая заявка порождает 10 вызовов СК и 60 с опроса |
| Веб → core-app, REST | TimeOut | 2 с | REST-запросы не должны ждать СК — ответ формируется из БД |
| core-app → веб, WebSocket | TimeOut | 60 с + 5 с запас | соединение живёт не дольше окна ожидания; после закрытия клиент показывает «опрос завершён» |
| core-app → веб, WebSocket | Retry (reconnect) | экспоненциальный backoff 1, 2, 4 с, до 5 попыток, затем `GET` состояния | обрыв сети у клиента не должен приводить к потере уже полученных предложений |
| Продюсеры и консьюмеры Kafka (core-app, osago-aggregator) | Retry + DLQ | 3 попытки с backoff, затем DLQ | временные ошибки Kafka или схемы не блокируют партицию |
| osago-aggregator → СК, «создать заявку» | TimeOut | 5 с | медленная СК не должна задерживать отправку заявки в остальные |
| osago-aggregator → СК, «получить предложение» | TimeOut | 3 с | опрос короткий и частый; длинный таймаут съедает окно 60 с |
| osago-aggregator → СК, «создать заявку» | Retry | 3 попытки, backoff 1, 2, 4 с, только при сетевой ошибке / 5xx и с идемпотентным ключом (id заявки) | без идемпотентного ключа повтор создаст дубликат заявки в СК; «получить предложение» не повторяется — следующий цикл опроса и есть повтор |
| osago-aggregator → СК, оба эндпоинта | Circuit Breaker, отдельный на каждую СК | открывается при 50 % ошибок из последних 20 вызовов или при 5 таймаутах подряд; открыт 30 с; half-open — 3 пробных вызова | «лежащая» СК не тратит потоки и соединения, её предложение сразу помечается как `error`, остальные СК продолжают работать |
| osago-aggregator → СК, оба эндпоинта | Rate Limiter, отдельный на каждую СК | лимит из договора с СК (token bucket, общий на все экземпляры — в Redis) | мы не должны делать с партнёрами то, что партнёр делал с нами (проблема №2 из описания компании) |

Оценка нагрузки на СК в пике: 2 500 активных заявок × 10 СК = 25 000 опрашиваемых заявок;
при опросе каждые 3 с это ≈ 8 300 исходящих запросов в секунду без ограничений. Такой поток ни
одна СК по договору не примет, поэтому Rate Limiter на каждую СК обязателен, а интервал опроса
адаптивный: `max(3 с, активных заявок у СК / лимит СК)`. Если СК принимает, например, 200 RPS,
2 500 заявок опрашиваются по кругу каждые 12,5 с — это укладывается в окно 60 с, но означает,
что предложение может прийти клиенту с задержкой до ~12 с после решения СК. Если СК поддерживает
webhook или батч-запрос «предложения по списку заявок», адаптер этой СК переключается на него —
интерфейс адаптера от этого не меняется.

Что намеренно **не** применяется:

- Retry на вызове «получить предложение» — лишний: неудачный опрос просто повторится в следующем
  цикле.
- Circuit Breaker между core-app и osago-aggregator — нет синхронного вызова, Kafka уже даёт
  буферизацию и повторную доставку.
- Retry на `POST /osago/requests` со стороны веб-приложения без идемпотентного ключа — иначе
  возможны дубли заявок; фронтенд передаёт `Idempotency-Key`, и core-app возвращает уже созданную
  заявку.

## 5. Redis (Managed Service for Redis) — новый контейнер

Добавлен для двух задач, которые появляются только из-за нескольких экземпляров сервисов:

1. **Pub/Sub для WebSocket.** Предложение из Kafka читает один экземпляр core-app, а WebSocket
   клиента может быть открыт на другом. Экземпляр-получатель публикует событие в канал
   `osago:{id заявки}`, все экземпляры подписаны и отправляют событие в свои сокеты. Состояние
   самих соединений нигде не хранится — после переподключения клиент получает пропущенное через
   `GET`.
2. **Распределённый token bucket** лимитов СК — лимит из договора общий на все экземпляры
   osago-aggregator, локальный лимитер в каждом поде превысил бы его в N раз.

Redis не является источником правды: потеря данных в нём означает лишь повторное переподключение
клиентов и кратковременное «обнуление» счётчиков лимитов.

## 6. Несколько экземпляров сервисов — зависит ли решение

Да, и решение построено с учётом этого:

| Вопрос | Решение |
|---|---|
| Какой экземпляр osago-aggregator обрабатывает заявку | Консьюмер-группа Kafka: партиции `osago.requests` распределяются между экземплярами, один id заявки всегда в одной партиции |
| Кто опрашивает СК по заявке после отправки | Экземпляр, взявший заявку, записывает в БД `lease` (свой id, срок 15 с) и продлевает его при каждом цикле. Фоновая задача в каждом экземпляре раз в 5 с подбирает заявки с истёкшим lease — так заявка «упавшего» пода перехватывается в течение ~15 с без дублирования опроса |
| Повторная доставка команды из Kafka после ребалансировки | Идемпотентность по id заявки: уже известная заявка не создаётся в СК повторно |
| Лимиты вызовов СК | Общий token bucket в Redis (раздел 5) |
| Circuit Breaker на СК | Локальный в каждом экземпляре: это допустимо, состояние «СК недоступна» каждый экземпляр обнаружит самостоятельно за несколько вызовов, а централизация добавила бы сетевой вызов в каждый запрос |
| Доставка предложения в WebSocket нужного клиента | Redis Pub/Sub (раздел 5); WebSocket-сессии не требуют sticky-балансировки, но балансировщик должен поддерживать апгрейд соединения |
| Масштабирование | core-app и osago-aggregator остаются stateless (состояние — в PostgreSQL, Kafka, Redis), поэтому HPA из задания 2 применим к обоим; число партиций `osago.requests` задаёт потолок параллелизма osago-aggregator — заложено 12 партиций |
