# Задание 5. Проектирование GraphQL API сервиса client-info

Файлы:

- `schema.graphql` — схема GraphQL (SDL): типы, перечисления, корневые запросы.
- `examples.graphql` — примеры запросов по сценариям продажи и обслуживания страховок.
- Этот документ — анализ REST-контракта и пояснение решений.

## 1. Анализ Swagger-контракта client-info

### 1.1. Ресурсы и операции

| Ресурс | Операция | Ответ |
|---|---|---|
| `/clients/{id}` | `GET` — карточка клиента по id | `Client { id, name, age }` |
| `/clients/{id}/documents` | `GET` — документы клиента | `[Document { id, type, number, issueDate, expiryDate }]` |
| `/clients/{id}/relatives` | `GET` — родственники клиента | `[Relative { id, relationType, name, age }]` |

Ключевая сущность — **Клиент**; **Документ** и **Родственник** — вложенные объекты карточки,
доступные только через клиента (нет ресурсов `/documents/{id}` или `/relatives/{id}`).
Все операции — чтение; в контракте нет операций создания и изменения данных, нет фильтров,
пагинации и выбора полей.

### 1.2. Что в этой структуре создаёт проблему

1. **N запросов на один сценарий.** Оформление ОСАГО требует карточку и документы — два запроса;
   семейный продукт — карточку и родственников; личный кабинет — карточку, контакты, документы.
   С ростом числа групп данных (контракт описывает только три из них, а атрибутов в карточке до
   500) число ресурсов и запросов на сценарий растёт линейно. Именно это команда и наблюдает как
   кратный рост RPS client-info.
2. **Нет выбора полей.** `GET /clients/{id}/documents` всегда возвращает все документы со всеми
   полями, хотя для ОСАГО нужны только паспорт и водительское удостоверение, а для страхования
   жизни — только паспорт. Фильтрацию делает потребитель, трафик и время сериализации тратятся
   впустую. Единый ресурс «вся карточка» неприемлем по той же причине, только в большем масштабе.
3. **Слабая типизация.** `type` документа и `relationType` — свободные строки, даты — строки без
   формата; каждый потребитель интерпретирует их по-своему.
4. **Нет пакетных операций.** Сервис взаиморасчётов, обрабатывая реестр, запрашивает клиентов по
   одному (`N × GET /clients/{id}`).
5. **Версионирование через путь (`/v1`)** означает, что любое расширение карточки — это либо новый
   ресурс, либо новая версия API для всех потребителей сразу.

Вывод: проблема не в количестве атрибутов, а в том, что REST заставляет выбирать между «много
мелких ресурсов» (много запросов) и «один большой ресурс» (много лишних данных). GraphQL снимает
этот выбор: один запрос, в котором потребитель сам перечисляет нужные группы и поля.

## 2. Схема GraphQL

### 2.1. Сущности и поля

| Тип | Поля из контракта (имена сохранены) | Добавлено | Зачем добавлено |
|---|---|---|---|
| `Client` | `id`, `name`, `age` | `birthDate`, вложенные `documents`, `relatives`, `contacts`, `address` | Вложенные поля — основной механизм: потребитель выбирает группы карточки в одном запросе. `contacts` и `address` показывают, как добавляются следующие группы из 500 атрибутов без новых ресурсов |
| `Document` | `id`, `type`, `number`, `issueDate`, `expiryDate` | `issuedBy` | Пример расширения без ломающих изменений |
| `Relative` | `id`, `relationType`, `name`, `age` | `birthDate` | — |
| `Contact` | — | `id`, `type`, `value`, `verified` | Группа карточки, нужная личному кабинету; в REST v1 ресурса не было |
| `Address` | — | почтовые поля | Группа карточки, нужная оформлению полиса |

Перечисления `DocumentType`, `RelationType`, `ContactType` заменяют свободные строки контракта,
скаляр `Date` — строковые даты. Поля `age` остаются ради обратной совместимости (вычисляются из
`birthDate`).

Nullability: `id`, `name`, типы и номера — обязательные (`!`), остальное — nullable, так как в
реальной карточке эти атрибуты могут быть не заполнены; списки всегда возвращаются (пустой список
вместо `null`), чтобы потребителю не нужно было различать «нет данных» и «нет поля».

### 2.2. Запросы (queries) и покрытие REST-операций

| REST-операция | GraphQL |
|---|---|
| `GET /clients/{id}` | `client(id: ID!): Client` — выбираются только нужные поля |
| `GET /clients/{id}/documents` | `client(id) { documents(types: [...]) { ... } }` — вложенное поле с фильтром по типу |
| `GET /clients/{id}/relatives` | `client(id) { relatives(relationTypes: [...]) { ... } }` — вложенное поле с фильтром по степени родства |
| `N × GET /clients/{id}` (реестры) | `clients(ids: [ID!]!): [Client]!` — пакетная загрузка |

Документы и родственники сделаны **полями клиента, а не отдельными корневыми запросами**
(`documents(clientId)`), потому что:

- в предметной области они не существуют вне клиента — так же, как в REST они были вложенными
  ресурсами;
- именно вложенность позволяет получить карточку, документы и родственников одним запросом;
- отдельные корневые запросы вернули бы проблему «N запросов на сценарий» в новой обёртке.

Фильтры (`types`, `relationTypes`, `types` у контактов) — необязательные аргументы: без них поле
возвращает полный список, как делал REST. Пагинация не вводится: списки документов и родственников
у одного клиента короткие (единицы записей), а cursor-пагинация усложнила бы клиентов без выгоды.
Для пакетного запроса `clients` разумный лимит — 100 id за запрос, он проверяется резолвером.

### 2.3. Как это снижает нагрузку

| Сценарий | REST v1 | GraphQL |
|---|---|---|
| Оформление страхования жизни | 2 запроса, все документы | 1 запрос, только паспорт |
| Оформление ОСАГО | 2 запроса, все документы | 1 запрос, паспорт + ВУ + СТС |
| Семейный продукт | 2 запроса | 1 запрос, только супруг и дети |
| Личный кабинет (шапка) | 1 запрос, вся карточка | 1 запрос, имя и контакты |
| Реестр на N клиентов | N запросов | 1 запрос |

Число HTTP-запросов к client-info на сценарий падает до одного, объём ответа — до реально
используемых полей. Примеры запросов для каждого сценария — в `examples.graphql`.

## 3. Решения по реализации (вне схемы, но влияют на нагрузку)

- **N+1 внутри сервиса.** Запрос `clients(ids)` с вложенными `documents` не должен превращаться в
  N запросов к БД: резолверы вложенных полей загружают данные пакетно (DataLoader —
  один `SELECT ... WHERE client_id IN (...)` на группу).
- **Ограничение сложности запроса.** Так как потребитель сам формирует запрос, сервис ограничивает
  глубину (достаточно 3 уровней) и «стоимость» запроса, чтобы один потребитель не мог запросить
  карточки 10 000 клиентов со всеми группами — это тот же Rate Limiting, что и в задании 4, только
  по стоимости запроса, а не по числу вызовов.
- **Кеширование.** Карточка клиента меняется редко; ответы на `client(id)` кешируются по id с
  коротким TTL, инвалидация — при изменении данных клиента в client-info.
- **Эволюция без версий.** Новые группы атрибутов добавляются новыми полями `Client`; старые поля
  помечаются `@deprecated`, а не удаляются, поэтому потребители переходят в своём темпе и
  путь `/v1` больше не нужен.
- **Мутации.** Контракт v1 содержит только чтение, поэтому в схеме — только `Query`. Операции
  записи, которые сервис выполняет при оформлении страховки (создание и обновление карточки,
  документов, контактов), добавляются следующим шагом как `Mutation` с input-типами
  (`createClient`, `updateContacts`, `addDocument`), не меняя описанные запросы.
- **Переход потребителей.** REST v1 и GraphQL работают параллельно; веб-приложение и core-app
  переводятся на GraphQL по сценариям, после чего REST-ресурсы выводятся из эксплуатации.
